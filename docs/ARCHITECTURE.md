# Ajaia Docs — Architecture Note

## Product Slice

Ajaia Docs focuses on a reliable document lifecycle:

**Authenticate → Create/Import → Edit → Save → Reopen → Share**

The assignment is intentionally timeboxed, so the implementation prioritizes a complete and reliable core workflow rather than attempting to reproduce the full Google Docs feature set.

Real-time collaboration, comments, version history, and complex enterprise permissions were intentionally excluded from the core build.

## Frontend

The frontend uses React, TypeScript and Vite.

Authentication state is managed through `AuthContext`, while API communication is centralized in the API service layer.

The main product surfaces are:

* Login
* Document dashboard
* Document editor
* File import
* Sharing workflow

The editor uses formatted HTML for document content. This was selected because HTML maps naturally to the browser-based formatting requirements and allows formatting to be persisted and restored without introducing a custom document model.

## Backend

FastAPI provides the REST API layer.

The backend is organized around:

* API routes
* Pydantic schemas
* SQLAlchemy models
* Repository/data-access logic
* Service/business logic
* Authentication and authorization

JWT tokens identify the authenticated user.

Business authorization is handled server-side rather than relying only on frontend visibility.

## Data Model

### Users

Stores the identities used for authentication and document ownership/sharing.

```text
users
-----
id
name
email
password_hash
created_at
```

### Documents

Stores document metadata and content.

```text
documents
---------
id
title
content
owner_id
created_at
updated_at
```

The document content contains the formatted HTML generated by the editor.

### Document Shares

Sharing is represented through a separate relationship:

```text
document_shares
---------------
id
document_id
user_id
permission
created_at
```

Keeping sharing separate from ownership allows a document to have multiple shared users and leaves room for additional permission types in the future.

## Authentication

JWT-based authentication is used because the assignment requires a lightweight user/access model rather than enterprise identity integration.

The application includes seeded demo accounts so reviewers can immediately test the sharing workflow.

## Authorization

Document access is checked on the backend.

A user can access a document when:

* They own the document, or
* They have a valid share record for that document.

Editing requires appropriate edit access.

Only the document owner can manage sharing and delete the document.

This ensures that authorization is enforced even if a user attempts to call the API directly.

## Persistence

SQLite is the local development default because it requires no external database service.

For production deployment, the same SQLAlchemy data model is used with PostgreSQL through the configured `DATABASE_URL`.

This keeps local setup simple while providing a production-ready relational database option.

## File Import

The core file workflow supports:

* `.txt`
* `.md`

Files are limited to 2 MB.

Imported content is decoded as UTF-8 and converted into safe editable HTML.

Markdown is intentionally treated as imported text rather than introducing a full Markdown processing pipeline. This keeps the assignment implementation small and reduces unnecessary dependency and security surface while still demonstrating the complete file-import workflow.

## Validation and Error Handling

The application validates important user inputs including:

* Authentication credentials
* Document information
* File type
* File size
* Document access
* Share target

API errors are returned through appropriate HTTP responses and surfaced to the user through the frontend rather than exposing raw backend exceptions.

## Testing

The backend includes automated tests focused on document authorization and sharing behavior.

The authorization test is intentionally meaningful because it verifies that access control is enforced rather than only testing whether an endpoint returns a successful HTTP response.

## Tradeoffs

### HTML Editor Instead of a Heavy Editor Framework

A lightweight browser editor was chosen because the required formatting set is small and the assignment has a strict timebox.

### JWT Instead of OAuth

The assignment allows seeded or mocked users, so JWT authentication provides a practical implementation without introducing external identity-provider configuration.

### TXT/MD Instead of DOCX

TXT and Markdown demonstrate the file-upload/import workflow while avoiding the additional complexity of Office document parsing.

### No WebSockets

Real-time collaboration requires synchronization, conflict resolution, connection management, and potentially a collaborative document model. Implementing that within the same timebox would risk the reliability of the mandatory features.

## Scope Prioritization

The implementation prioritized:

1. Complete document lifecycle
2. Rich-text editing
3. Persistence
4. File import
5. Sharing and authorization
6. Deployment
7. Testing
8. Documentation

This prioritization ensures that the reviewer can test a coherent end-to-end product flow.
